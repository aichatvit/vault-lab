# Ключевая схема и жизненный цикл секретов

## Ключи VLAGOST2

Для индекса и каждого файла выводятся отдельные пары ключей CBC и HMAC.
Применяется KDF_TREE с HMAC-ГОСТ Р 34.11-2012-256, двумя итерациями и 512 битами
выхода по формуле ниже. Для индекса label равен ASCII `vault-lab/v2/index`,
seed — 16-байтовому ID контейнера. Для файла label равен ASCII
`vault-lab/v2/file`, seed — `ID контейнера || LE64(ID файла)`. Первые 32 байта
результата — ключ «Кузнечика» CBC, следующие 32 байта — ключ HMAC.

- Тег индекса покрывает 52 байта заголовка, IV индекса и его шифротекст.
- Тег каждого блока вычисляется от
  `ASCII("VLAGOST2") || ID контейнера || LE64(ID файла) || LE64(номер блока) || LE32(логическая длина блока) || LE32(длина IV) || IV || шифротекст`.
  Нумерация блоков начинается с нуля. Привязка к ревизии выполняется через
  список ожидаемых тегов в индексе. Формат блока остаётся пригодным для
  копирования между рабочей папкой и контейнером.
- Для рабочего индекса и состояния сеанса, сохранённых вместе в `state`,
  используется label `vault-lab/v2/work-index` и seed
  `ID контейнера || ID сеанса`. ID сеанса — 16 случайных байт. После повторной
  аутентификации ключи выводятся снова. На диск записываются открытые
  идентификаторы и зашифрованные аутентифицированные метаданные.

Каждое шифрование использует свежий случайный IV и PKCS#7. Сравнение тегов
выполняется за постоянное время. Перед расшифровкой подтверждаются HMAC блока
и его соответствие ожидаемому тегу. Копирование записи требует тех же проверок
целостности. Замена всего контейнера корректной старой ревизией требует
внешней привязки к ожидаемой ревизии для обнаружения.
Формат парольной разблокировки подлежит отдельному согласованию.
[Двоичная раскладка](DATA_FORMAT.md#vlagost2--формат-s-box)

## Выработка ключей

Пусть HMAC256 — HMAC-ГОСТ Р 34.11-2012-256, предоставленный плагином.
Конкатенация обозначена `||`. Для i = 1, 2 приложение формирует:

```text
input_i = BYTE(i) || label || 00 || seed || 02 00
T_i     = HMAC256(M, input_i)
K       = T_1 || T_2
K_enc   = K[0:32]
K_mac   = K[32:64]
```

Последние `02 00` обозначают 512 бит выходного материала, а не длину входного
сообщения. Счётчик занимает один байт (r=1). Значения label и seed задаются по типу записи. Идентификаторы в seed открыты. Разделение ключей позволяет не использовать
один ключ непосредственно и для CBC, и для HMAC.

Linux-плагин не экспортирует используемый API KDF_TREE. Приложение формирует
входные строки KDF, а каждый HMAC исполняет плагин. Совпадение с контрольным
вектором RFC 7836 проверяет `kdf_rfc7836_vector`; это не сертификация реализации.

## Создание, ввод, хранение

`keygen` берёт 32 байта из `getrandom` и однократно печатает их в hex. Команды
хранилища требуют ровно 64 ASCII hex-символа. Регистр hex несущественен.
Ввод выполняется через `rpassword`, без отображения. Параметра `--key`,
переменной окружения для ключа и файла ключей в приложении нет.

Мастер-ключ не записывается в контейнер и не оборачивается другим ключом.
Восстановления, escrow, PBKDF, проверки сложности пароля и защиты слабого
выбранного вручную ключа нет. Используйте результат генератора и отдельный
случайный ключ для каждого хранилища. Храните ключ отдельно от резервных копий.

## Время жизни в памяти

Ввод, декодированный ключ, материал KDF, дополненные данные и расшифрованные
индексы и блоки используют `Zeroizing`.
Это обеспечивает очистку соответствующих управляемых буферов при освобождении,
но не обещает отсутствие копий в нативной библиотеке, терминале, ядре или swap.
Содержимое файлов обрабатывается по блокам.
Приложение отключает core dumps и dumpability. `mlock` и защита от root-чтения
памяти не реализованы.

## Замена ключа

Для записи под новым ключом создайте отдельный контейнер и перенесите файлы
через смонтированные представления. После закрытия проверьте новую упаковку
с новым ключом. Резервные копии старого контейнера продолжают открываться
старым ключом. Удаление обычного файла лишь освобождает его место в файловой системе.
