# Формат S-BOX и Windows SD-Reader

Основание — PR-SBOX v1.0.1 от 18.11.2026 и согласованный сценарий работы с контейнером. Документ описывает реализацию `VLAGOST2` в Linux и проект Windows SD-Reader с тем же сценарием работы.

## Согласованные условия

- Для Windows доступен криптоплагин того же поставщика. Байтовую совместимость с Linux предстоит подтвердить на тестовых снимках.
- В Linux консольная утилита, а в Windows SD-Reader распаковывают контейнер в служебную папку на диске. Каждый пользовательский файл хранится в ней отдельным зашифрованным файлом.
- Данные расшифровываются в памяти по запросу, а изменения шифруются перед записью на диск. Переносимый контейнер собирается заново при закрытии на обеих платформах.
- Интеграция с Проводником требует файлового слоя, который выдаёт расшифрованные данные без сохранения их локальной копии. Штатная загрузка содержимого через CFAPI сохраняет полученные байты на диске, поэтому для выдачи открытых данных этот механизм не подходит. Реализация файлового слоя ещё не выбрана. Буква диска остаётся отдельной опцией. [Загрузка содержимого в CFAPI](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfhydrateplaceholder)

## Формат для Linux и Windows

Для нового сценария принят **`VLAGOST2`**. Переносимый контейнер — один файл со служебным заголовком, зашифрованным индексом и зашифрованными записями файлов. Записи делятся на блоки до 1 МБ и имеют одинаковую раскладку в контейнере и в обычных файлах служебной папки. Криптографический контекст блока сохраняется при упаковке и распаковке, поэтому приложение проверяет и копирует шифротекст без повторного шифрования содержимого. Внутренняя файловая система в виде образа не требуется. [Двоичная раскладка](DATA_FORMAT.md#vlagost2--формат-s-box)

Размеры и квоты указываются в десятичных единицах. **1 МБ = 1 000 000 байт, 1 ГБ = 1 000 МБ.** Квота задаётся при создании и применяется к логическим размерам пользовательских файлов. Рабочая папка, зашифрованные метаданные и новая упаковка требуют дополнительного места.

Утилита Linux принимает 32-байтовый мастер-ключ. Для транспортного режима PR-SBOX-08 требует пароль с проверкой парольной политики. Схему разблокировки мастер-ключа паролем предстоит согласовать. Режимы сессии Secret Disk и списков разрешённых АРМ требуют отдельной интеграции с Secret Disk и КА. [Ключевая схема](KEY_MANAGEMENT.md#ключи-vlagost2)

## Общий сценарий работы в Linux и Windows

В Linux `open FILE` распаковывает контейнер, а `exit` закрывает сеанс и упаковывает изменения. При использовании `mount FILE DIRECTORY` упаковка выполняется после размонтирования. В проекте Windows те же операции запускаются через интерфейс SD-Reader. [Команды Linux](CLI.md)

1. **Открытие.** Пользователь указывает контейнер и проходит аутентификацию. Приложение проверяет целостность и удерживает блокировку на время сеанса, чтобы другой экземпляр не перезаписал тот же контейнер. При ошибке доступ к содержимому не открывается.
2. **Распаковка.** Приложение создаёт служебную папку, проверяет зашифрованные блоки и копирует записи в отдельные файлы, по одному на каждый пользовательский файл. Зашифрованный индекс связывает служебные идентификаторы с именами, каталогами и размерами. Временные файлы с содержимым и метаданными тоже шифруются до записи. Доступ к дереву открывается после завершения распаковки.
3. **Работа с файлами.** Пользователь обращается к файлам через консольный клиент или виртуальную папку. Приложение проверяет целостность запрошенных данных и расшифровывает их в памяти. Создание, изменение, переименование и удаление обновляют зашифрованную рабочую копию и её индекс. Исходный контейнер на диске остаётся последней упакованной версией до закрытия.
4. **Упаковка и закрытие.** Пользователь завершает сеанс. Приложение прекращает принимать новые операции и завершает текущие записи. При наличии изменений оно создаёт новый индекс и копирует актуальные зашифрованные записи во временный контейнер на том же томе. После записи, синхронизации и проверки нового контейнера приложение атомарно заменяет исходный файл. Затем оно отзывает доступ к дереву, удаляет служебную копию и освобождает блокировку. Успешное закрытие подтверждается после завершения этих операций.
5. **Восстановление.** Если упаковка прервана до замены, исходный контейнер и зашифрованная рабочая копия сохраняются для повторной попытки. Состояние сеанса должно позволять после сбоя отличить незавершённую упаковку от завершённой замены с незавершённой очисткой. Ошибка закрытия видна пользователю. Возобновление работы с содержимым требует повторной аутентификации.

### Структура рабочей папки

| Что хранится | Содержимое |
|---|---|
| Зашифрованный файл на каждый пользовательский файл | Служебное имя по идентификатору и поколению, шифротекст содержимого и данные проверки целостности. |
| Зашифрованный индекс | Исходные имена, дерево каталогов, идентификаторы и логические размеры файлов. Каталоги представлены записями индекса. |
| Зашифрованное состояние сеанса | Данные для восстановления согласованной рабочей копии и определения этапа упаковки после сбоя. |

На Linux `state` содержит зашифрованный полный снимок либо зашифрованный журнал со ссылкой на аутентифицированный контрольный снимок. Рабочий файл содержит версии блоков `VLAGOST2`, а зашифрованный индекс хранит смещения актуальных записей. Доступ после повторной аутентификации восстанавливается из мастер-ключа и идентификаторов контейнера и сеанса. [Раскладка записей](DATA_FORMAT.md#запись-файла) · [Выработка ключей](KEY_MANAGEMENT.md#ключи-vlagost2)

## Операции в продуктовом формате

Проект предусматривает один переносимый файл с зашифрованным индексом и записями файлов. Каждая запись может содержать несколько независимо проверяемых зашифрованных блоков. Такая раскладка позволяет распаковывать и упаковывать контейнер последовательно с ограниченным объёмом памяти. Во время сеанса изменения сохраняются в служебной папке, а при закрытии переносимый файл собирается заново.

| Операция | Проектируемое поведение |
|---|---|
| Создать | При создании задаётся предельный объём пользовательских данных. В новом контейнере сохраняется начальный индекс с корневым каталогом. |
| Открыть или проверить | После аутентификации проверяются заголовок и индекс. При распаковке и полной проверке последовательно проверяются блоки файлов. |
| Просмотреть и прочитать | Список файлов берётся из рабочего индекса. По запросу приложение читает нужные блоки из зашифрованного файла в служебной папке и расшифровывает их в памяти. |
| Создать файл или каталог, записать или изменить размер файла | Приложение проверяет доступную квоту и согласованно обновляет зашифрованные данные и индекс рабочей копии. |
| Переименовать или переместить внутри | Приложение меняет имя или родительскую ссылку в рабочем индексе. Служебный идентификатор файла остаётся прежним. |
| Скопировать или перенести внутрь либо наружу | При копировании внутрь приложение проверяет квоту и шифрует данные до записи. При переносе источник удаляется после подтверждения записи назначения. Явно выгруженный файл хранится по правилам места назначения. |
| Удалить содержимое | Приложение исключает файл из рабочего индекса и удаляет соответствующий зашифрованный файл. При упаковке в контейнер входят только актуальные записи. Квота сохраняется. |
| Закрыть или восстановиться после сбоя | Приложение упаковывает сохранённые изменения, заменяет контейнер и очищает служебную папку. При прерванной упаковке рабочая копия позволяет повторить операцию. |
| Передать или скопировать контейнер целиком | Передаётся один файл после успешной упаковки и закрытия. На другом устройстве он открывается после аутентификации и проверки целостности. Переданная копия самостоятельна. |
| Удалить контейнер целиком | Удаляется файл закрытого контейнера. Переданные копии и ранее выгруженные файлы остаются на своих устройствах. |
| Сменить пароль или ключ | Поведение зависит от выбранной схемы получения или разблокировки ключа. Для продуктового формата эта схема ещё не утверждена. |

### Метаданные продуктового формата

Открытый заголовок содержит сигнатуру, ID контейнера и ревизии, длины IV и шифротекста индекса. Зашифрованный индекс содержит квоту, дерево каталогов, размеры файлов и ожидаемые теги блоков. Из индекса вычисляются расположение и длины записей. Перед открытием дерева приложение проверяет заголовок, индекс и все блоки, копируемые в рабочую папку. Правила переноса времён, владельцев и прав между платформами предстоит согласовать. [Зашифрованный индекс](DATA_FORMAT.md#зашифрованный-индекс)

#### Место на диске

На время упаковки место требуется одновременно для исходного контейнера, зашифрованной рабочей копии и нового контейнера. Приложение учитывает свободное место на диске отдельно от квоты пользовательских данных. Если места не хватает, приложение сообщает об ошибке и сохраняет рабочую копию для повторной упаковки.

#### Примеры размера контейнера

Расчёт для одного файла `file.bin` и корневого каталога, при IV длиной 16 байт и полных блоках по 1 МБ. На каждый блок добавляется 64 байта в записи данных и 32 байта тега в индексе. Остальные расходы включают заголовок, метаданные двух узлов, IV, тег и выравнивание индекса.

| Размер пользовательских данных | Блоков | Служебные данные и защита | Размер контейнера |
|---:|---:|---:|---:|
| 1 МБ | 1 | 0,000292 МБ | 1,000292 МБ |
| 100 МБ | 100 | 0,009796 МБ | 100,009796 МБ |
| 1 ГБ | 1 000 | 0,096196 МБ | 1,000096196 ГБ |
| 10 ГБ | 10 000 | 0,960196 МБ | 10,000960196 ГБ |

Это логический размер упакованного файла. Расход на диске зависит также от размера файлов и имён, параметров плагина и выделения блоков файловой системой. Рабочая папка и временная упаковка учитываются отдельно.

## Защита рабочей папки и завершение сеанса

- Доступ к служебной папке ограничивается учётной записью процесса. Авторизованный пользователь работает через консольный клиент или виртуальную папку. Приложение шифрует перед записью на диск содержимое файлов, индекс и служебные данные, необходимые для восстановления.
- При закрытии файловый слой прекращает выдавать данные через прежний путь, в том числе по ранее открытым дескрипторам. После сбоя или перезагрузки повторный доступ к рабочей копии требует новой аутентификации.
- Приложения, получившие расшифрованные данные, могут записать собственные временные файлы или копии вне рабочего каталога контейнера. Требование шифрования таких копий, файла подкачки и дампов памяти обеспечивается отдельно настройками приложений и ОС.

## Скорость копирования через FUSE в Linux

Следующие серии показывают эволюцию реализации. Измерения интегрированной версии приведены в разделе «Результаты после внедрения».

Файл размером 24 МБ со случайными данными дважды скопировали из `/tmp` в смонтированную папку `./opened` командой `cp --reflink=never --sparse=never`. Измерение охватывало запись с шифрованием в рабочую копию. Упаковка контейнера после размонтирования и побайтовая сверка выполняются за пределами этого интервала.

| Прогон | Время `cp`, с | Скорость, МБ/с |
|---:|---:|---:|
| 1 | 5,663 | 4,238 |
| 2 | 5,652 | 4,246 |

Средняя скорость двух прогонов составила **4,24 МБ/с**. Дополнительный `fsync` занял менее 1 мс в каждом прогоне. `cmp` подтвердил совпадение байтов с исходным файлом в обоих прогонах. Тестовые файлы удалены.

### Разбор затрат записи

В Linux флаг `--benchmark-xor` включает замер без загрузки криптоплагина.
Используйте отдельный контейнер и синтетические данные. Режим использует
фиксированный тестовый ключ и фиктивный тег, поэтому содержимое доступно для
чтения и подмены любому, у кого есть файл. У контейнера сигнатура `VLAXOR01`,
у состояния рабочей папки — `VLAXWORK`.

```bash
./target/debug/vault-lab --benchmark-xor init ./xor-bench.sbox --quota-mb 100
mkdir -p ./xor-opened
sudo ./target/debug/vault-lab --benchmark-xor mount ./xor-bench.sbox ./xor-opened
```

Копируйте тестовый файл в `./xor-opened` из другого терминала. После
размонтирования проверьте упаковку командой
`./target/debug/vault-lab --benchmark-xor check ./xor-bench.sbox` от учётной
записи с доступом к файлу. Для сравнения используйте обычный контейнер на том
же диске и тот же тестовый файл.

Отдельный стенд записывал 24 МБ случайных данных напрямую через `Store::update` в release-сборке. Стенд подменял весь криптоплагин на XOR с фиктивным тегом для тестовых файлов. Размер записей, алгоритм копирования поколения и синхронизация оставались одинаковыми. Замер относится к слою хранения, а число 4,24 МБ/с выше — к копированию через FUSE.

| Файловая система | Порция записи | Штатный плагин, МБ/с | XOR-стенд, МБ/с |
|---|---:|---:|---:|
| NTFS, первая серия | 131 072 байта | 3,33–3,40 | 8,81–9,34 |
| NTFS, первая серия | 1 МБ | 27,9–28,6 | 71,0–71,5 |
| tmpfs | 131 072 байта | 4,36 | 34,3 |
| tmpfs | 1 МБ | 38,1 | 244 |

На tmpfs при порциях по 131 072 байта один прогон со штатным плагином занял 5,51 с. Из них 2,59 с ушло на шифрование с HMAC и 2,10 с — на проверку и расшифровку прежних блоков. При записи полными порциями по 1 МБ предыдущие блоки не расшифровывались. При обеих реализациях криптографии мелкие записи суммарно скопировали 2,12 ГБ зашифрованных префиксов между поколениями файла. Порции по 1 МБ сократили этот объём до 0,276 ГБ.

В дополнительной серии на NTFS с порциями по 131 072 байта суммарное время вызовов `fsync` варьировалось от 1,77 до 16,95 с. В прогонах с долгой синхронизацией она занимала большую часть времени даже на XOR-стенде. Повторная инициализация плагина для итогового `check` в одном прогоне вернула ошибку 507 после измерения записи и упаковки.

### Кэш последнего блока

Последний проверенный блок хранится в памяти. Повторное чтение или частичное изменение использует его только после совпадения тега индекса и всех байтов зашифрованной записи на диске. Полная перезапись блока использует только новые данные.

Сравнение в release-сборке через слой хранения:

| Файловая система | Операция | До оптимизации, МБ/с | После, МБ/с |
|---|---|---:|---:|
| NTFS | Запись 24 МБ порциями по 131 072 байта | 3,36 | 4,65 |
| NTFS | Запись 24 МБ порциями по 1 МБ | 28,50 | 28,12 |
| tmpfs | Запись 24 МБ порциями по 131 072 байта | 4,66 | 7,40 |
| tmpfs | Чтение первых 2 МБ запросами по 4 096 байт | 0,19 | 21,0 |
| tmpfs | Запись 24 МБ порциями по 1 МБ | 40,0 | 39,6 |

Замер выполнялся напрямую через слой хранения со штатным плагином. Записи синхронизировались после каждого запроса. Этот замер сделан при прежней схеме копирования неизменных префиксов.

### Дописывание рабочих блоков

После оптимизации изменённые блоки дописываются в рабочий файл. Индекс
хранит смещения актуальных версий. При уплотнении приложение переносит
только актуальные записи. Зафиксированный индекс позволяет восстановить
сеанс после прерванной записи.

Парный замер на NTFS, 24 МБ случайных данных, release-сборка, штатный
криптоплагин. Запись выполнялась через слой хранения.

| Порция записи | До, МБ/с | После, МБ/с | Суммарный `fsync` до и после, с |
|---|---:|---:|---:|
| 131 072 байта | 4,66 | 7,43 | 1,78 → 0,46 |
| 1 МБ | 27,90 | 39,99 | 0,24 → 0,06 |

В первом сценарии прежний алгоритм копировал 2,12 ГБ неизменных префиксов.
Новый записал 169 МБ зашифрованных блоков с учётом уплотнений. Это объём,
переданный файловой системе, без пересчёта в физические записи накопителя.
Переносимый контейнер упаковывается в логическом порядке блоков.
[Формат рабочего состояния](DATA_FORMAT.md#рабочая-папка-linux)

### Группировка последовательных записей по 1 МБ

Linux-утилита собирает мелкие последовательные записи в один блок из
1 000 000 байт исходных данных. На диск записывается зашифрованный блок с
IV, дополнением и тегом. Неполный блок сохраняется при `fsync`,
закрытии файла или штатном завершении сеанса. До этого авария процесса
может привести к потере остатка в памяти.

В парном замере на NTFS со штатным плагином записали 24 МБ порциями по
131 072 байта. Через слой хранения скорость выросла с **7,46–7,51 МБ/с**
до **39,62–40,00 МБ/с**. Объём зашифрованных записей снизился с 169 МБ
до 24 МБ. Прочитанные данные сверены с исходными после каждого прогона.

### Исходные замеры перед оптимизацией по типам нагрузки

Замеры на Linux, NVMe с NTFS (`ntfs3`), release-сборка, десятичные МБ. Временный стенд вызывал код рабочего хранилища напрямую. Для проверки большого дерева и создания мелких файлов он также вызывал обработчики `VaultFs` напрямую. Точка `./opened` в момент проверки была обычной папкой, устройство `/dev/fuse` отсутствовало. Время записи включает сброс последнего блока. Упаковку измеряли отдельно. После повторного открытия данные побайтно сверяли с исходными. В таблице приведён диапазон двух прогонов каждого сценария со штатным плагином.

| Сценарий | Полезная скорость, МБ/с | Что происходило в рабочей папке |
|---|---:|---|
| Один файл, 24 МБ, порции по 131 072 байта | 37,6–39,2 | 24,002 МБ записей данных и 72 вызова `sync_all` |
| Тот же файл, три входных запроса по 8 МБ | 44,8–45,0 | Те же блоки по 1 МБ, три фиксации индекса и 9 вызовов `sync_all` |
| Два файла, всего 24 МБ, получатель меняется после каждых 131 072 байт | 4,52–4,53 | 159,35 МБ записей данных с учётом уплотнений, 629 вызовов `sync_all` |
| 64 правки по 4 096 байт по кругу в восьми разных блоках существующего файла | 0,085–0,086 | 0,262 МБ полезных изменений, 113,01 МБ записей данных с учётом уплотнений |
| Создание, запись и сброс 200 файлов по 4 096 байт | 0,57–0,58 | 1 400 вызовов `sync_all` и 3,53 МБ записей индекса на 0,819 МБ полезных данных |
| Один файл, 24 МБ, порции по 131 072 байта, в дереве уже есть 10 000 пустых каталогов | 26,9–27,5 | 8,42 МБ записей индекса. В парном тесте с одним файлом и без дополнительных каталогов — 0,018 МБ и 37,2–37,6 МБ/с |

Объёмы в таблице получены подсчётом байтов, переданных файловой системе. Время `sync_all` включает ожидание файловой системы и накопителя. Физическое число записей NVMe и накладные расходы ядра FUSE в этих опытах не измерялись.

**Один большой файл.** Из 0,61–0,64 с на запись 24 МБ операции CBC и обработка данных в HMAC заняли в сумме 0,49–0,50 с, синхронизация — 0,056–0,072 с. Контрольный сценарий со встроенным тестовым XOR дал 236 МБ/с. Для ускорения обычного копирования стоит обрабатывать несколько независимых блоков одновременно и передавать готовые записи одному писателю в порядке смещений. Проба в памяти на 48 блоках по 1 МБ дала 32,8–34,3 МБ/с с одним потоком, 50,3–51,2 с двумя и 67,4–69,8 с четырьмя. В интервал включено создание отдельного контекста плагина на каждый поток. Шифротекст каждого блока после замера расшифрован и сверен. Для интеграции нужны ограниченная очередь, обработка ошибок плагина, проверка многопоточной работы нативной библиотеки и измерение через реальный mount. Один запуск стенда завершился ошибкой 507 при создании контекста. В таблицу вошли полные прогоны.

**Чередующиеся записи.** В `Store` один буфер на всё хранилище. Переключение файла фиксирует незаполненный блок. Экспериментальный буфер на каждый из двух файлов сократил объём записей со 159,35 до 24,002 МБ, число синхронизаций с 629 до 75 и дал 37,5–39,2 МБ/с. В рабочей реализации нужен общий предел памяти с вытеснением буферов и учётом всех принятых байтов в квоте. Чтение должно видеть принятые изменения, а `fsync` и синхронная запись — дожидаться фиксации нужного файла. [Буферизация в Store](../src/store.rs)

**Правки внутри файла.** Каждая малая перезапись сразу попадает в `update`. Часть прежнего блока нужно сохранить, поэтому обработчик читает старую запись, проверяет её, объединяет изменения в памяти и заново шифрует блок. При уплотнении заодно копируются остальные актуальные записи. Для серии правок в одних и тех же блоках стоит испытать ограниченный кэш изменённых блоков по паре «файл, номер блока». При обязательном `fsync` после каждой правки возможность объединения ограничена. Для такого профиля имеет смысл отдельно сравнить меньшие независимо аутентифицируемые записи в рабочей папке, сохранив транспортные блоки по 1 МБ.

**Индекс и синхронизация.** При фиксации блоков приложение синхронизирует файл данных, записывает и синхронизирует временный индекс, заменяет `state` и синхронизирует каталог. Оно также клонирует дерево и карту рабочих файлов, проверяет и шифрует весь индекс. При обычном дописывании `update` обходит даже предшествующие блоки, а проверка квоты в FUSE суммирует размеры всех узлов для каждого запроса. Первые изменения для большого дерева — хранить счётчики занятого места и размера индекса, обходить только затронутый диапазон вне уплотнения. Для множества мелких файлов стоит испытать зашифрованный аутентифицированный журнал изменений с периодическим полным снимком. При пакетной фиксации важно сохранить порядок «данные, затем индекс» и проверить восстановление при сбое до и после публикации. [Фиксация рабочего состояния](../src/store.rs) · [Проверка квоты](../src/fs.rs) · [Сериализация дерева](../src/format.rs)

**Упаковка.** При закрытии изменённого сеанса приложение проверяет HMAC каждого блока при копировании во временный контейнер, затем повторно читает и проверяет готовый контейнер перед заменой исходного. В опыте с одним файлом на 24 МБ это заняло 0,48 с. Вариант с проверкой тега по индексу при копировании и полной проверкой HMAC готового контейнера перед заменой занял 0,26 с. В отдельной проверке изменение байта шифротекста в рабочем файле привело к отказу упаковки, исходный контейнер сохранился побайтно. При свежем открытии есть отдельная стоимость распаковки — чтение и проверка контейнера целиком и синхронизация каждого созданного рабочего файла. Опыты не измеряли скорость открытия.

Эта серия относится к предыдущей реализации и временным прототипам. Результаты интегрированной версии приведены ниже.

В каждом сценарии он повторно открывает закрытый контейнер и сверяет все байты. Для сравнения использованы исходные замеры тех же нагрузок на этом томе. Упаковка одного последовательного файла на 24 МБ заняла 0,257–0,287 с при исходном времени около 0,48 с. Программа проверяет теги при копировании и полностью проверяет HMAC готового контейнера перед его установкой. Создание множества мелких файлов по-прежнему требует отдельной фиксации метаданных.

Рабочая реализация группирует до восьми блоков на сеанс, шифрует независимые блоки двумя контекстами и фиксирует соседние блоки одной транзакцией. Квота учитывает принятые данные всех файлов. После успешного `fsync` рабочее состояние содержит все изменения указанного файла. При аварии до синхронизации могут потеряться данные из буферов объёмом до 8 МБ. ## Проверки для приёмки VLAGOST2 на обеих платформах

- Снимок с бинарными файлами и вложенными папками, упакованный в Linux, открывается в Windows, а упакованный в Windows — в Linux. Состав дерева и байты файлов совпадают. При неверном ключе, повреждении снимка или несовместимом заголовке содержимое остаётся закрытым.
- При распаковке в Linux и Windows каждый пользовательский файл появляется в служебной папке в зашифрованном виде. При чтении и записи приложение сохраняет на диске только зашифрованные файлы, индекс и временные данные. Проверка включает частично завершённые операции.
- Через консольный клиент Linux и виртуальную папку Windows файлы можно открыть, создать, изменить, переименовать и удалить. После упаковки и повторного открытия сохраняются имена и байты оставшихся файлов. Удалённые записи отсутствуют. Конфликтующее имя вызывает явную диагностику либо обрабатывается по согласованным правилам.
- После штатного закрытия доступ через прежний путь и ранее открытые дескрипторы прекращается. Рабочая папка удалена, контейнер готов к передаче. Ошибка закрытия видна пользователю.
- На обеих платформах проверяются параллельные обращения, сбой до и после замены контейнера, перезагрузка и нехватка места при распаковке или упаковке. После сбоя сохраняются проверяемый контейнер и данные, необходимые для завершения операции. Повторный доступ к содержимому требует аутентификации.
- Сценарии проходят на каждой заявленной версии Windows и Windows Server. Отдельно проверяются файловый перенос и совместимость Linux-платформ, требования к паролю, квотам и аудиту по мере их реализации.
